# Release plan: default departments, guideline availability and saved guideline requests

Branch `feat/default-departments-guideline-requests`. Written for whoever runs the release (the project owner).
Nothing here has been run against the hosted project; every step was rehearsed on the local stack only.

## What is released

| Part | Change |
|---|---|
| Database | Three forward-only migrations: `20261120120000_default_departments`, `20261120130000_guideline_availability`, `20261120140000_user_requests` |
| Edge Function | `delete-department` only: a default department's refusal is answered `409 {"errorCode":"default-department"}` instead of `409 conflict` (new file `errors.ts`). The database still decides every refusal. |
| Website | The frontend of this branch (via `develop` → Vercel) |
| Compliance service | Unchanged; no restart needed |
| Other Edge Functions | Unchanged |

## Why the order is: database, then the Edge Function, then the website

Checked against the code:

- **New database, old website**: works. The migrations only add a column, a trigger, a table and functions; every
  existing function keeps its signature and grants. The old website can still try to delete a default department:
  the database refuses it, and the old website shows a generic message. Nothing is lost.
- **New website, old database**: partly broken (the Requests pages would show "Some requests couldn't be loaded",
  and Check Compliance without a guideline would say it couldn't check). So the website goes **last**.
- **New Edge Function, old database**: harmless (the new mapping only adds one case). **Old Edge Function, new
  database**: a default department's deletion is refused with `conflict`; still safe. So the function can go at any
  time after the database; do it right after.

No maintenance window is required, and nobody has to be signed out. Still, pick a quiet time and tell the team that
`develop` must not receive other pushes until step 6 is done (every push to `develop` deploys the website).

## 0. Before the day

1. Merge the branch into `develop` through a pull request **only when ready to release**. `develop` deploys the
   website at once, and the website must go after the database (see above). If you merge earlier, the Requests pages
   show their load error until the database is migrated. Safer: keep the PR open until step 5.
2. Confirm the hosted migration history ends at `20261119140000` (SQL Editor):
   ```sql
   select version from supabase_migrations.schema_migrations order by version desc limit 3;
   ```
   If anything newer than `20261119140000` is there, stop and reconcile first.
3. Dry-run the backfill (read-only), to know which departments will be marked:
   ```sql
   select o.name as organization, d.id, d.name, d.is_quality, d.requires_compliance_check
   from public.departments d join public.organizations o on o.id = d.organization_id
   where d.removed_at is null and d.deletion_job_id is null
     and ((d.name = 'Pharmacovigilance' and d.requires_compliance_check and not d.is_quality)
       or (d.name = 'Quality Assurance' and d.is_quality))
   order by 1, 3;
   ```
   Expect two rows per organization. An organization with fewer is left as it is (the migration prints a NOTICE); its
   departments simply aren't protected until an owner decides what to do.
4. Check that no department has a pending file cleanup in a way that would block the backfill (informational):
   ```sql
   select id, name from public.departments where deletion_job_id is not null and removed_at is null;
   ```

## 2. The database migrations

```bash
supabase link --project-ref <project ref>
supabase migration list         # remote ends at 20261119140000
supabase db push --dry-run      # must list exactly these three, nothing else:
                                #   20261120120000_default_departments
                                #   20261120130000_guideline_availability
                                #   20261120140000_user_requests
supabase db push
```

If the dry run lists anything else, stop. Each migration runs in one transaction; if one fails, `db push` stops there
and that migration leaves nothing behind.

**Do not run `seed.sql` on the hosted project.** (It now sets `system_key` for MedCare's local seed departments; on
the hosted project the backfill in `20261120120000` does that.)

## 3. Check the database

```sql
-- Two default departments per organization (or the organizations reported by the migration's NOTICE):
select o.name, count(*) filter (where d.system_key = 'pharmacovigilance') as pv, count(*) filter (where d.system_key = 'quality-assurance') as qa
from public.organizations o left join public.departments d on d.organization_id = o.id group by o.name order by 1;
-- The guard is in place:
select tgname from pg_trigger where tgrelid = 'public.departments'::regclass and tgname = 'departments_default_guard';
-- The new functions, for signed-in users only:
select p.proname, has_function_privilege('authenticated', p.oid, 'execute') as signed_in, has_function_privilege('anon', p.oid, 'execute') as anonymous
from pg_proc p where p.pronamespace = 'public'::regnamespace
  and p.proname in ('guideline_availability', 'submit_user_request', 'cancel_user_request', 'decide_user_request');
-- The new table: row level security on, read-only for signed-in users, nothing for anon:
select relrowsecurity from pg_class where oid = 'public.user_requests'::regclass;
select grantee, privilege_type from information_schema.role_table_grants where table_name = 'user_requests' and table_schema = 'public';
```

Expected: `pv = 1` and `qa = 1` per organization; the trigger listed; `signed_in = true`, `anonymous = false`;
`relrowsecurity = true`; only `authenticated | SELECT` (plus the owner). Compare the row counts with step 1: they must
be identical (the migrations add no row to existing tables).

## If something goes wrong

- **A migration fails** during `db push`: that migration is rolled back automatically; the earlier ones stay. They
  are safe on their own (see the order above). Fix the cause or undo with the script below; don't deploy the website.
- **After step 2 or later**, to undo the database: first **export the saved requests** (they are lost otherwise):
  ```sql
  select * from public.user_requests order by created_at;   -- save the result
  ```
  Then run `supabase/scripts/rollback_default_departments_guideline_requests.sql` as `postgres` in the SQL Editor, and
  mark the three versions reverted:
  ```bash
  supabase migration repair --status reverted 20261120140000 20261120130000 20261120120000
  ```
  Then redeploy the previous website (revert the merge on `develop`) and the previous `delete-department`
  (`git checkout <previous commit> -- supabase/functions/delete-department`, deploy, then restore the branch's files).
  The rollback leaves the audit rows written by request decisions (`organization_management_audit`, action
  `decide-request`); they are history and harmless.
- **The website misbehaves but the database is fine**: revert the merge on `develop` (Vercel redeploys the previous
  website). The old website works with the new database (see the order above).
